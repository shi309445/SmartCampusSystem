## 竖切看：离线 vs 在线

```
              离线（建库）                    在线（问答）
                   │                              │
第 1 层 数据层   ●──────────────────────────────  │
                   │                              │
第 2 层 处理层   ●──────────────────────────────  │
                   │                              │
第 3 层 存储层   ●──────────────┐                │
                   │            │                │
                   │            ▼                │
第 4 层 检索层     │         ●──────────────────●
                   │            │                │
第 5 层 生成层     │            │             ●──●
                   │            │                │
第 6 层 应用层     │            │             ●──●
                   │            │                │
                   └────────────┴────────────────┘
                                ▼
                              答案
```



- **离线**：第 1 → 2 → 3 层，跑一次建底库
- **在线**：第 4 → 5 → 6 层，每次提问跑一遍
- **交汇点**：第 3 层存储层

## 四个关键规律

1. **每层都是 5 个子层**，结构统一：理解 → 获取 → 加工 → 组织 → 保障
   （注意：为了对称，几个真实环节被塞进了别人的格子里——见文末「三个最容易漏掉的环节」）
2. **第 3 层是分水岭**：下面建库（离线），上面问答（在线）
3. **第 6 层是闭环口**：反馈从这层回流，优化第 1~5 层
   （前提是能归因到具体某一层——见「现象 → 定位到哪一层」）
4. **第 3 层同时是一份契约**：编码器版本 / 向量维度 / 元数据字段 / 权限字段，必须离线侧和在线侧一致，否则检索会静默失效

## 做减法：先分三档

六层 × 5 格 = 30 个格子。全都做，等于什么都做不好。先回答一个问题：**哪些是"没有它就跑不起来"的？**

| 档位 | 含义 | 判断标准 |
| :--- | :--- | :--- |
| **必需** | 没有它就不是 RAG | 缺了功能不成立 |
| **生产必需** | 能跑但不敢上线 | 缺了会出事（答错 / 越权 / 查不到原因） |
| **进阶** | 没有也能跑，只是不够好 | 优化项，按痛点加 |

> **图上怎么看档位**：30 个格子按三档着色，并统一坐在每条色带内的**白色托盘**上（这样格子的浅色底不会和色带的蓝 / 橙底糊在一起）。档位看四处：**边框颜色 + 边框粗细/虚实 + 圆点形状 + 标题字色**——**绿粗实线＋实心圆 ●＝必需，玫红实线＋菱形 ◆＝生产必需，灰虚线＋空心圆 ○＝进阶**（必需 13 格 / 生产必需 12 格 / 进阶 5 格）。
> 注意两套标识互不干扰：**底色**（蓝 / 橙）说的是离线 / 在线，**格子**说的才是档位。而且**档位落在格子上，不落在整层上**——同一层里既有必需也有进阶，比如第 3 层的"向量化"是必需，"关联（三元对齐）"是进阶。

### 必需档：最小可用 RAG 七步

```text
数据源 → 解析切分 → 嵌入 → 向量库 → 相似度召回 → 拼上下文 → 生成
 1 层      2 层      3.1    3.2/3.3      4.2          5.1      5.3
```

说白了就是 **第 1、2、3、5 层的极简版**：能把资料喂进去、能按相似度捞出来、能拼给模型答，就已经是一个能用的 RAG。第 4 层的排序 / 过滤 / 改写、第 6 层的会话 / 呈现，**先做最笨的版本**。

### 生产必需档：能跑，但不敢上线

| 项 | 属于哪层 | 缺了会怎样 |
| :--- | :--- | :--- |
| **权限过滤**（检索时就按租户 / 角色过滤） | 4.3 | 越权看到别人的数据 |
| **重排**（cross-encoder / LLM 重排） | 4.4 | 正确内容排在第 8 位，等于没检索到 |
| **引用溯源**（每句话能指回原文块） | 5.4 | 答案无法核验，用户不敢信 |
| **拒答兜底**（低置信就说"不知道"） | 5.5 | 一本正经地编 |
| **检索评测**（召回率 / 忠实度 / 归因） | 横切 | 出事不知道该改哪一层 |
| **增量更新与删除**（含合规删除） | 3.5 | 库是旧的；该删的删不干净 |
| **缓存**（嵌入 / 检索 / 语义 / 前缀） | 横切 | 又贵又慢，重复问题重复花钱 |

### 进阶档：按痛点加，别一开始就上

| 项 | 什么时候才需要 |
| :--- | :--- |
| **查询改写 / HyDE / 多查询** | 用户问法口语化、指代多，和文档用词对不上 |
| **混合检索 + RRF 融合** | 专有名词、编号、缩写多，纯向量召回不稳 |
| **父子块**（小块检索、大块返回） | 切分粒度和答案完整性互相打架 |
| **多跳检索 / 查询分解** | 一个问题要串起好几处证据 |
| **知识图谱 / GraphRAG** | 需要跨文档的关系推理、全局性提问 |
| **多模态解析**（表格 / 图片 / 扫描件） | 数据源里有大量非纯文本 |
| **注入防护**（把检索内容当数据，不当指令） | 库里的文档不可信、可能被人写入 |
| **Agentic RAG**（模型自己决定查几次） | 固定流程已经不够用 |

### 落地顺序

```text
阶段 1：最小可用七步        → 先让它能答
阶段 2：生产必需七项        → 先让它敢上线
阶段 3：按痛点加进阶项      → 哪里疼补哪里
阶段 4：图谱 / 多模态 / Agentic → 到这一步说明你是少数派了
```

**最大的坑不是"缺功能"，而是"过早复杂"**：切分没调好就上 GraphRAG、召回没评测就上重排、权限没做就上多模态——每一层都要维护、调试、付钱。

## 现象 → 定位到哪一层

"反馈回流"那条箭头看着很美，但**没有归因，这条箭头是断的**：用户点了个踩，你不知道该改哪层。实战里最有用的不是那张六层图，而是下面这张表。

| 用户看到的现象 | 最可能的问题层 | 具体查什么 |
| :--- | :--- | :--- |
| 答案里的信息**根本没检索到** | 4.2 召回 / 3.1 向量化 / 2.3 切分 | 先看 top-k 里有没有那个正确块：没有 → 召回或切分；有但排太后 → 4.4 重排 |
| 检索到了，**答案没用上** | 5.1 上下文 / 5.2 提示词 | 块是不是被截断在窗口外、是不是落在中间被忽略、指令有没有要求"只依据资料回答" |
| 检索回来一堆**不相关的** | 4.1 查询理解 | 多轮指代没消解（"那它呢"）、口语和文档用词不一致 |
| 答案对，但**引用错** | 5.4 后处理 | 引用编号和块的映射错位；一个块被拆成多段后编号丢失 |
| **越权**看到别的租户内容 | 4.3 过滤 | 过滤是在召回后还是召回前？多路召回里有没有一路绕过了过滤 |
| 内部术语 / 缩写**查不到** | 3.1 向量化 | 领域词不在编码器词表里；考虑混合检索，或补一份同义词表 |
| 昨天能查到，今天**查不到** | 3.5 维护 | 增量更新把旧块删了、版本没对齐 |

**四个必备度量**（缺了上面这张表就只能靠猜）：

- 检索侧：`召回率@k`（该找到的找到了吗）、`MRR`（该靠前的靠前吗）
- 生成侧：`忠实度`（有没有编）、`答案相关性`（有没有答在点上）

判断口径很简单：**检索指标高、生成指标低 → 问题在第 5 层（尤其 5.1 上下文组织、5.2 提示词）；检索指标低 → 问题在第 4 层及以下的建库环节**（切分、编码、过滤、重排）。

## 三个最容易漏掉的环节

为了"每层 5 个子层"的整齐，下面三个真实环节被塞进了别人的格子里。实战中它们经常就是故障源。

1. **查询向量化**（藏在 4.1 / 4.2 里）
   提问也要过一次编码器。**入库和查询必须用同一个编码器、同一版本**——版本错配，向量空间不对齐，检索会**静默失效**（不报错，只是什么都查不到）。所以第 3 层不只是"分水岭"，它还是一份契约面：编码器版本、向量维度、元数据字段、权限字段，离线在线两侧必须一致。

2. **多路召回的分数融合**（藏在 4.2 里）
   向量分和关键词分不在一个量纲上，直接相加是错的。用 RRF（倒数排名融合），或者先归一化再加权。

3. **上下文工程**（被 4.5 和 5.1 切成两半）
   去重、按 token 预算裁剪、按"重要内容放头尾"重排（模型对中间内容最不敏感）、加引用编号、需要时用父块补全。这一段的顺序和取舍，往往比换一个更强的模型更能提升答案质量。
